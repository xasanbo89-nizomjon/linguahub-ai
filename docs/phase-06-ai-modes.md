# Phase 6 — Secure AI Mode System

Date: 2026-08-06

## 1. Audit (pre-phase state)

Confirmed before writing any code: `server.js` kept a `SYSTEM_PROMPTS` object keyed by free-text display strings (`"General AI"`, `"Codex AI"`, ...), looked up via `buildSystemPrompt(mode)` which fell back to `SYSTEM_PROMPTS["General AI"]` on *any* unrecognized key - meaning a typo, a stale client, or a deliberately crafted `mode` value silently got the general-purpose prompt instead of an error. `validateChatBody` only checked that `message` was a non-empty string under `MAX_MESSAGE_LENGTH`; `mode` itself was never validated and defaulted with `req.body.mode || "General AI"` - any string was accepted. `handleChat`/`handleChatStream` both hardcoded `model: "gpt-4.1-mini"` - there was no per-mode model, temperature, or output-token control at all. The frontend `#mode-select` used plain `<option>Text</option>` elements with no `value` attribute, so the option's visible label *was* the value sent to the backend - the frontend and backend were coupled through free text, not a stable contract. Every request sent exactly one system message plus one user message (`parsed.message`) - no prior conversation turns were ever included, confirmed unchanged from the Phase 5 audit. Image AI/Web Search/Voice AI existed as selectable options with real-looking system prompts (e.g. "You are LinguaHub Image AI. Help create image prompts...") despite having no actual image/search/voice provider integration anywhere in the codebase - selecting them just ran the same text-chat completion under a different prompt, which is exactly the kind of faked capability this phase was required to eliminate.

## 2. Central AI mode registry (`lib/aiModes.js`)

A new backend-only, `Object.freeze`d module is now the single source of truth for every mode's full configuration: `id`, `label`, `description`, `enabled`, `capability`, `provider`, `model`, `systemPrompt`, `temperature`, `maxInputChars`, `maxOutputTokens`, `timeoutMs`, `reasoning`, `tools`, `authRequired`. Seven stable, lowercase-hyphenated ids replace the old display-string keys: `general`, `codex`, `cyber`, `deep-thinking`, `image`, `voice`, `web-search`. `isValidModeId()`/`getModeConfig()` are the only ways to resolve a mode by id from outside the module; an unknown id returns `null` (never a silent default). Immutability is real, not just documented: each mode object and its `tools` array are individually frozen, then the whole `MODES` map is frozen - a mutation attempt under strict mode throws `TypeError` (verified by test, and confirmed the value is genuinely unchanged afterward, not just that an exception happened to fire).

## 3. Public mode metadata (`GET /api/ai/modes`)

`toPublicMetadata(mode)` returns exactly `{ id, label, description, enabled, capability }` - `getPublicModes()` maps every mode through it. `systemPrompt`, `model`, `temperature`, every limit, `tools`, `provider`, and `authRequired` never leave the backend process. A new route, `GET /api/ai/modes`, registered alongside `/health`/`/api/auth/me` (before the `/api/*` 404 catch-all so it isn't swallowed by it), returns `{ modes: aiModes.getPublicModes() }`. Verified live: the response body contains no `gpt-4`, no `sk-`, and none of `"systemPrompt"`, `"temperature"`, `"tools"`, `"provider"`, `"model"` as JSON keys (automated in `tests/aiModes.test.js` and `tests/ai-modes-request.test.js`, re-confirmed with a live `curl` against the real running server).

## 4. Request schema and validation

`validateChatBody` was fully rewritten. It accepts either the new `{ messages: [...], mode }` shape or the legacy single-message `{ message, mode }` shape (backward compatible, tested). Any of `aiModes.FORBIDDEN_REQUEST_FIELDS` (`model`, `systemPrompt`, `system`, `temperature`, `maxTokens`, `max_tokens`, `tools`, `reasoning`) present anywhere in the body is **rejected with 400**, not stripped-and-ignored - a client that tries to override the model or system prompt gets an honest error, not a request that silently proceeds without its attempted override. `mode` is resolved and validated explicitly: omitted → defaults to `general`; present but not a string → 400 "Invalid mode"; a string that isn't a real id → 400 "Unknown mode"; a real but currently-disabled id (`image`/`voice`/`web-search`) → 400 "... is not available yet." **Nothing here silently substitutes the default mode for an explicit-but-invalid request** - `resolveModeOrDefault()` exists in the registry for a different purpose (normalizing already-stored conversation metadata) and is deliberately not used on this live request path. Every entry in a `messages` array must have `role` of exactly `user` or `assistant` - a client-supplied `role: "system"` is rejected outright (400 "Invalid message role"), never folded into or replacing the real system prompt. The final message in the array must be from the user. Verified live and in `tests/ai-modes-request.test.js` (15 tests).

## 5. System prompt ownership

Every system prompt is authored once, in `lib/aiModes.js`, and is the *only* system message ever sent to the provider - `lib/contextBuilder.js`'s `buildContext()` always prepends exactly one `{ role: "system", content: mode.systemPrompt }` and nothing in the request path can add, override, or duplicate it (a client-sent `system`/`systemPrompt` field is a 400 per §4; a client-sent `role: "system"` message is dropped per the context builder's own filtering, verified by test). No prompt text is ever echoed back to the client in a success or error response, a log line, or the public metadata endpoint (verified: `console.error(error)` in the error handlers logs only the caught `Error`/provider error object, never the constructed `messages` array).

## 6. Model allowlist

`ALLOWLISTED_MODELS` is derived automatically from the models actually assigned to enabled modes (`gpt-4.1-mini`, `gpt-4.1`) - not a separately-maintained list that could drift. Both were **verified live** against this project's real OpenAI API key before being assigned in the registry (a direct `chat.completions.create` call to each, confirmed a genuine completion came back) - not assumed from documentation. Because `model` is a forbidden request field (§4), the allowlist is enforced structurally: there is no code path where a client-supplied string ever reaches the `model` parameter of an OpenAI call: the model is only ever read from `mode.model` inside `handleChat`/`handleChatStream`, after `mode` was resolved server-side from a validated id.

## 7. Limits and cost control

Each mode owns its own `maxInputChars`, `maxOutputTokens`, and `timeoutMs` (Codex: 12000/2048/60000; General/Cyber: 8000/1024-1536/60000; Deep Thinking: 8000/2048/90000 - a larger budget matching its purpose). A bug was found and fixed during testing: the pre-existing global `MAX_MESSAGE_LENGTH` env-based default (8000) was being applied as an unconditional `Math.min()` floor under every mode's own limit, silently capping Codex's higher 12000-char allowance back down to 8000 and defeating the entire point of per-mode limits. Fixed so the env var (`MAX_MESSAGE_LENGTH_OVERRIDE`) is `null` unless an operator explicitly sets it - when unset, each mode's own configured limit is authoritative; when set, it acts as an additional operator-imposed ceiling on top of (never above) the mode's own limit. Verified live before and after the fix: a 9000-character message was rejected under `general` (8000 limit) but accepted and reached the real model under `codex` (12000 limit) only after the fix. `handleChatStream` additionally now bounds total generation time to the resolved mode's own `timeoutMs` via a `setTimeout`-triggered `abortController.abort()`, layered alongside (not replacing) the pre-existing, must-be-preserved `res.on("close", ...)` client-disconnect abort - a `clientDisconnected` flag distinguishes the two cases in the catch block so a timeout (connection still open) gets an honest error message written to the stream, while a real client disconnect stays a silent no-op exactly as before.

## 8. Context building (`lib/contextBuilder.js`)

A new, single function (`buildContext(mode, rawMessages, options)`) is now the only place either route assembles the exact array sent to the provider - used identically by `handleChat` and `handleChatStream`, so the two can never drift apart. It sanitizes incoming messages (drops anything that isn't `role: user|assistant` with non-empty string `content`, per-message-truncates to the resolved limit), then trims from the **oldest** end if the combined context exceeds a character/message-count budget, while always keeping the final (current) user message even if it alone would exceed the budget - the user's actual question is never the thing silently dropped. This was a deliberate architecture extension beyond Phase 5's single-message request: Task 5 (regenerate/retry must preserve mode and re-derive context) and Task 9 (context building) both require it, and Deep Thinking specifically benefits from seeing prior turns. Verified live: a three-turn exchange (name given, acknowledged, then asked back) correctly returned the name from a fresh, stateless HTTP request - proving context genuinely threads through, not just accepted-and-ignored.

## 9. Frontend: mode selector (`www/mode-ui.js`)

New module, loaded before `app.js`, owning `#mode-select` end to end. `init(selectEl)` fetches `GET /api/ai/modes` once and builds one `<option>` per mode from the response - the frontend never invents a mode id, capability, or "available" state of its own. A disabled mode's `<option>` gets `disabled = true` and its visible label gets an honest `" (unavailable)"` suffix (native `<select>` disabled-option behavior - no fake enabled state, no hidden option, no tooltip-only warning). If the endpoint can't be reached (backend down, offline launch), `init()` falls back to a small static `OFFLINE_FALLBACK_MODES` list whose enabled/disabled split is kept in sync with the real registry by test - the UI stays usable rather than showing an empty selector, and `usedFallback: true` is reported so a caller could surface that state if desired. Per-mode empty-state prompt suggestions (General/Codex/Cyber/Deep Thinking each have their own themed set) replace the old single hardcoded list; real, honest prompt starters only - no suggestions exist for the three disabled modes (they fall back to General's list, which a user could never actually see there since the select won't let them land on a disabled option in the first place).

## 10. Frontend: request schema and mode persistence (`www/app.js`)

`sendMessage()`/`handleRegenerateOrRetry()` now build a `messages` array (`buildMessagesForRequest()`) from the active conversation's stored history - user/assistant roles only, failed messages excluded, stopping right after the relevant message id - instead of sending a single string; `streamChat`/`fallbackChat` post `{ messages, mode }`, and the old `{ message, mode }` body is gone from the frontend entirely (the backend still accepts it for any other legacy caller, §4). Regenerate/retry pass the *user* message id that preceded the reply being redone, which naturally excludes the old (being-replaced) assistant answer and anything after it from the resent context. The mode selector is disabled (`modeSelect.disabled = busy`) for the full duration of an active generation, alongside the existing input-disabling in `setBusy()`. A conversation's `metadata.mode` is written on every send and read back on restore/regenerate - restoring a conversation only reselects its saved mode if that mode is still enabled (`LinguaHubModeUI.isSelectableMode`); an unknown or now-disabled saved mode leaves the selector on whatever it already shows rather than forcing an invalid or unavailable selection. Mode loading now genuinely gates the first conversation restore: `bootstrapModesAndHistory()` awaits `LinguaHubModeUI.init()` before calling `historyUI.start()`, so the first restore's mode-selection check always has real options to match against.

## 11. Frontend: legacy mode migration (`www/chatStore.js`)

`normalizeModeId()` maps every old Phase 1-5 display label (`"General AI"`, `"Codex AI"`, ...) to its new stable id, applied transparently wherever a conversation's `metadata.mode` is read from storage (`sanitizeConversation`), created (`createEmptyConversation`), or written through the public API (`updateConversation`). A conversation already sitting in a user's `localStorage` from before this phase, with `metadata.mode: "Cyber AI"`, reads back today as `"cyber"` with no data loss and no manual migration step - verified by test that patches raw pre-Phase-6 JSON directly into fake storage and confirms it reloads correctly. An already-stable but currently-unrecognized id is passed through unchanged rather than being silently rewritten - `chatStore.js`'s job is legacy-label normalization only; whether a given stable id is *currently enabled* is `mode-ui.js`'s concern, not the storage layer's.

## 12. Per-mode behavior

- **General AI** (`gpt-4.1-mini`, temp 0.7, 8000/1024): broad-purpose assistant, verified live with real prompts.
- **Codex AI** (`gpt-4.1-mini`, temp 0.3, 12000/2048): coding assistant; system prompt explicitly states it cannot execute code or access the filesystem/network/terminal and must never claim to have done so.
- **Cyber AI** (`gpt-4.1-mini`, temp 0.4, 8000/1536): defensive-security assistant; system prompt explicitly instructs it to explain vulnerabilities/attacks for defensive purposes while declining operational help for unauthorized access, credential theft, or malware for real-world unauthorized use, and states its own instructions are not a substitute for real authorization. **Verified live**: asked for step-by-step instructions to steal saved browser passwords from an unauthorized target, it declined and redirected to legitimate security/secure-coding help - not merely a source-code check of the prompt's wording, an actual model response.
- **Deep Thinking** (`gpt-4.1` - a deliberately different, stronger model - temp 0.4, 8000/2048, 90s timeout): structured, step-by-step reasoning for complex questions via prompt + model + larger output budget only; `reasoning: null` throughout - no provider "reasoning effort" API parameter exists for this model/integration, and none is faked (no artificial delay, no hidden chain-of-thought exposed as if it were a real reasoning-API feature).
- **Image AI / Voice AI / Web Search**: `enabled: false`, `capability: "unavailable"`, `provider`/`model`/`systemPrompt` all `null`. Selecting one is structurally impossible from the UI (disabled `<option>`); a direct API request for one is rejected with 400 before any prompt is built or provider called. No fallback "pretend chat" response is ever generated for these three - this was true before this phase for chat-completions-under-a-different-prompt, and remains categorically true now: there is no code path that runs a model call for a disabled mode.

## 13. Security

- **No system prompt, model name, or limit ever reaches the client** - enforced at the `toPublicMetadata()` boundary (§3) and re-verified against the live endpoint.
- **No client-supplied privileged field is ever silently accepted** - every one of `model`/`systemPrompt`/`system`/`temperature`/`maxTokens`/`max_tokens`/`tools`/`reasoning` is a hard 400, tested individually, live and automated.
- **No system-role injection** - a client-crafted `{ role: "system", ... }` message anywhere in the array is rejected at validation (never silently dropped-and-continued, never merged with the real prompt).
- **Disabled modes are honestly inert, not just hidden** - `provider`/`model`/`systemPrompt` are `null` in the registry itself, so even a hypothetical bug that bypassed the enabled check would have nothing real to call.
- **No secrets in errors or logs** - error responses remain the same sanitized strings used since Phase 1 (`"❌ Error connecting to AI"` / `"❌ Invalid OpenAI API key..."`); `console.error(error)` logs the caught error object only, never the constructed messages array or system prompt.
- CORS, Helmet/CSP, and the sliding-window rate limiter are all unchanged and re-verified live (see §16) - no new external dependency was added (`mode-ui.js` is a same-origin static file, `/api/ai/modes` is a same-origin route), so **no CSP directive needed to change, and none did** (byte-identical header, confirmed by `curl`).

## 14. Performance

`buildContext()`'s trimming keeps the per-request payload bounded (default 24,000-char/40-message context budget, independent of any single mode's per-message limit) rather than growing unboundedly with a long conversation. The mode registry lookup is an O(1) object-property read, done once per request. No additional network round trip was introduced for a single chat turn beyond the one-time `GET /api/ai/modes` fetch on app load (cached in `availableModes` for the session, not re-fetched per message or per mode switch).

## 17. Limitations

- Image AI, Voice AI, and Web Search remain genuinely unimplemented - this phase intentionally made their unavailability structural and honest rather than building fake/stubbed responses for them; adding real capability for any of them is out of scope here.
- `deep-thinking`'s "reasoning" is prompt/model/budget-driven only, not a provider reasoning-effort API feature - documented in §12, not hidden.
- The global `MAX_MESSAGE_LENGTH` env var, if an operator sets it, still applies uniformly as a ceiling across all modes rather than being configurable per mode - an intentional simplification (single, well-understood operator knob) rather than an oversight.
- `www/app.js`'s client-side `MAX_EDIT_LENGTH` (composer edit-textarea cap) stays a single conservative constant (8000) rather than varying per active mode's real limit (e.g. Codex's 12000) - a soft UX guard only; the backend remains authoritative and correctly enforces each mode's real limit regardless of what the client-side edit box allows through.
- No real browser/visual verification was possible in this environment (same standing limitation as every prior phase) - the mode selector's rendering, disabled-option styling, and empty-state suggestion cards are verified via real DOM-integration tests and live `curl`/HTTP checks, not an actual browser window.

## 20. Rollback notes

Every change is a source-level edit or an additive new file; no database, no migration, no new npm dependency, no CSP change. To roll back: revert the five modified files (§19), delete the ten created files (§18). A user's existing `localStorage` chat history is forward-compatible either way - `normalizeModeId` only runs on read/write within `chatStore.js` itself, so reverting the frontend doesn't corrupt anything already migrated (a `general`/`codex`/etc. id would simply stop matching `SYSTEM_PROMPTS`'s old display-string keys if `server.js` were rolled back independently of the frontend - rollback should be applied to both together, or the old frontend's `"General AI"`-style values restored via `LEGACY_MODE_ALIASES`' inverse, which was not needed here since no rollback was requested). No git commit was created.
